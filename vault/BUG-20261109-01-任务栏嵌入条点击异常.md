# BUG-20261109-01 修复：任务栏嵌入条点击后变成带标题栏的小窗、面板不展开

## 需要先读

- vault/14-位置外观增强需求包.md（T5 任务栏模式）
- vault/13a-左下角贴角模式.md（嵌入任务栏三条硬事实）
- src-tauri/src/taskbar.rs、src-tauri/src/window_policy.rs（`apply_taskbar_effects` / `toggle_taskbar_panel`）

## Bug 摘要与根因假设
- 实际表现（2026-11-09 用户真机截图）：任务栏模式下点击嵌入条，条变成带图标和「— □ ✕」按钮的经典标题栏小窗口，展开面板没有出现。
- 期望表现：点击嵌入条在任务栏上方左下角展开现有面板，再点或 Esc 收起；嵌入条保持无边框。
- 复现路径：设置 → 外观 → 界面模式选「任务栏嵌入条」→ 点击开始按钮旁的嵌入条。
- 影响范围：只影响 taskbar 模式（模块 14 T5）；island / classisland 不经过这些代码路径。
- 根因（读 tao 0.35.3 源码与本项目代码确认）：
  1. **标题栏**：tao 的 `to_window_styles` 给无边框窗口也保留 `WS_CAPTION | WS_SYSMENU | 最小化/最大化框`，只靠 `WM_NCCALCSIZE` 把非客户区算成 0。`taskbar::enter` 嵌入时只在原样式上叠加 `WS_CHILD`；子窗口没有 DWM 边框，点击激活后系统按经典样式画出标题栏。
  2. **面板不展开**：`snapshot()` 与 `enter()` 把任务栏自己的客户区（约 48px 高）当成 `work_area`。`taskbar_panel_rect` 按它 clamp，面板被压成任务栏高度并叠在任务栏上，看起来就是没展开。
  3. **展开状态错位**：嵌入条点击自己翻转 `TaskbarState.expanded`，Esc、通知等其它来源收起面板时这个标记不变，之后点击会反向切换（点一下没反应）。

## 选定方案
- 方案：用户报告后直接修复（拖动问题刚确认修好，本条是同轮真机反馈）。
  - 新增 `windows_impl::embedded_child_styles`：嵌入时去掉 `WS_POPUP | WS_CAPTION | WS_SYSMENU | WS_THICKFRAME | 最小化/最大化框` 与顶层扩展样式（`WS_EX_TOOLWINDOW | APPWINDOW | WINDOWEDGE | TOPMOST | DLGMODALFRAME`），只加 `WS_CHILD`；`WS_EX_NOACTIVATE` 保留。回滚路径同时恢复原扩展样式。
  - 新增 `monitor_work_area`：用 `MonitorFromWindow` + `GetMonitorInfoW` 取任务栏所在显示器的 `rcWork` 作为面板 clamp 区域。
  - 展开标记改由窗口策略同步：`apply_taskbar_effects` 按有效状态写 `set_strip_expanded`，变化时广播 `window://taskbar-state-changed`；点击走 `toggle_taskbar_panel`，按有效状态用 `strip_toggle_target` 求目标。
- 改动范围：`src-tauri/src/taskbar.rs`、`src-tauri/src/window_policy.rs`；前端与 IPC 签名不变。
- 风险点：去掉样式后嵌入条若不随任务栏渲染，会回到「条消失」问题（08-18 修复的 `WS_EX_TOOLWINDOW` 仍被去除，未回退）；面板改按显示器工作区定位，副屏任务栏需真机确认。

## 真机第 2 轮（2026-11-09）

- 现象：标题栏不再出现，但点击嵌入条没有任何反应。
- 只读取证（Win32 枚举窗口，未改动用户环境）：
  - 运行中的 dev 进程 12:34:30 启动，晚于源码修改，确认运行的是第 1 轮修复版本；主线程对 `SendMessageTimeout` 正常响应，排除卡死。
  - 嵌入条 `GWL_STYLE=0x54000000`（子窗口 + 可见 + 裁剪兄弟），标题栏样式已去掉；WebView2 各级子窗口铺满 140×48。展开面板（island）位置正确但处于隐藏状态。
  - 显示器 (0,0)-(2560,1440)，工作区也是 (0,0)-(2560,1440)；任务栏窗口在 (0,1438)-(2560,1486)，只露 2px：**用户的任务栏开启了自动隐藏**。
  - 前台窗口为最大化的 Chrome，矩形 (-8,-8)-(2568,1448)，按 2px 容差不算全屏，排除「全屏时隐藏」误判。
- 根因：
  4. 运行时巡检（2s）按**整个任务栏矩形**判断是否重挂。自动隐藏的任务栏每次滑入/滑出位置都会变，巡检随之把嵌入条拆下重挂；用户把鼠标移到底部唤出任务栏再点击时，嵌入条正被重建，点击丢失。嵌入条是任务栏的子窗口，本会随任务栏移动，位置变化根本不需要重挂。
  5. 重挂在巡检的后台线程执行，持有任务栏状态锁时调用 `SetParent`，后者同步等待嵌入条所在的主线程；若主线程恰在点击命令里等同一把锁，两边互等、应用卡死（本次取证时未发生，属潜在死锁）。
- 修复：
  - 新增纯函数 `taskbar_change_needs_reattach`：只在任务栏尺寸或 DPI 变化时重挂，位置变化忽略；任务栏 HWND / Explorer 进程变化与嵌入条失效的判断不变。
  - 巡检改为把重挂投递到主线程（`reattach_on_main_thread`），重挂后按窗口策略重放一次，面板几何与「展开/收起」标记回到实际状态。
  - 嵌入条点击与运行时重挂写入应用日志（info），失败写 warn，便于下次直接从日志判断点击是否到达。
- 测试：`auto_hide_slide_does_not_require_reattach`、`size_or_dpi_changes_require_reattach` 先 RED 后 GREEN。
- 复验：Rust 190 passed / 1 ignored，fmt / clippy（`-D warnings`）/ check 通过；本轮未改前端文件。待用户第 3 轮真机验证。
- 同时从日志发现的另一问题（本轮未修）：2026-11-09 12:27 任务栏短暂消失（`查找 Shell_TrayWnd 失败`）后，每 2 秒报一次「嵌入任务栏失败：无效的窗口句柄」直到应用重启。说明 Explorer 重启会连带销毁嵌入条窗口，而重挂只会重新 `SetParent` 旧句柄；`leave` 在 `SetParent` 失败时提前返回、不复位状态。模块 14 T5 的「重启 Explorer 后自动重挂」验收项因此不成立，需要重建嵌入条窗口，单独处理。

## 真机第 3 轮（2026-11-09）

- 现象：点击嵌入条时弹出一个写着「LuckyIsland 任务栏」（嵌入条窗口标题）的提示框，面板仍不展开。
- 取证：
  - 12:44 编译的版本已含「嵌入条点击」日志（可执行文件内可检索到该字符串），12:55 之后启动多次，日志中**没有任何点击记录**，即点击未到达 Rust 命令。
  - 只读按 z 序枚举 `Shell_TrayWnd` 子窗口：最上层是 `Windows.UI.Composition.DesktopWindowContentBridge`（Win11 任务栏 XAML 内容层，`WS_EX_NOREDIRECTIONBITMAP`），覆盖整条任务栏，内含 `Windows.UI.Input.InputSite.WindowClass` 输入子窗口；自动隐藏收起时它不可见，任务栏滑出时显示。
- 根因 6：XAML 内容层显示时排在嵌入条之上。它用合成渲染，透明处能看到嵌入条，但 HWND 命中测试把点击交给了它，嵌入条收不到鼠标。前几轮「滑动就重挂」时会顺带把嵌入条置顶，所以偶尔点得到；第 2 轮去掉滑动重挂后就一直被压住。
- 修复：新增 `strip_needs_raise` 与 `start_zorder_keeper`。后台线程每 100ms 用 `GetWindow(tray, GW_CHILD)` 只读检查嵌入条是否为最上层子窗口；不是时投递主线程 `SetWindowPos(HWND_TOP, SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE)`，同一时刻最多一个请求在途；置顶写 info 日志，按 5 秒合并计数（若资源管理器与我们反复抢层级，日志里的计数会持续偏高）。
- 测试：`strip_is_raised_whenever_it_is_not_the_top_child` 先 RED 后 GREEN。
- 复验：Rust 191 passed / 1 ignored，fmt / clippy（`-D warnings`）/ check 通过；本轮未改前端。待用户第 4 轮真机验证。

## 真机第 4 轮（2026-11-09）与方向调整

- 现象：仍然点不开。
- 取证：13:02 启动的版本日志里有多条「重新置顶」（6 秒内 28 次、24 次、11 次），说明资源管理器每次滑出任务栏都把 XAML 内容层排回最上层，与置顶守护来回抢；仍然**没有任何「嵌入条点击」记录**。主线程对 `SendMessageTimeout` 正常响应。
- 按 Bug 流程「卡住处理」（同一 bug 两次以上修复未通过验证）停下，用交互式问答请用户选方向：Rust 直接接管点击 / 先取证再定 / 本版本搁置任务栏模式。用户选择 **由 Rust 直接接管点击**。
- 修复（根因 7：点击由哪个窗口接收取决于资源管理器的层级排序，无法可靠保证落在嵌入条上）：
  - 新增 `src-tauri/src/taskbar_click.rs`：嵌入任务栏成功后在独立线程安装低级鼠标钩子（`WH_MOUSE_LL`），退出任务栏模式或重挂前卸下。回调只处理主按钮的按下/松开：按下在「完全露出的嵌入条」范围内才接管并吞掉；对应的松开一律吞掉，松开仍在嵌入条上才投递主线程切换面板。其余鼠标事件直接放行，不记录坐标。
  - 自动隐藏收起时嵌入条大部分在屏外，此时不接管，避免在屏幕底边误展开。
  - 回调只做原子读写和只读 Win32 查询（`IsWindowVisible`、`GetWindowRect`、`MonitorFromWindow`/`GetMonitorInfoW`、`GetParent`/`GetWindow`），不加锁、不发跨线程消息，避免拖慢全局鼠标。
  - 钩子线程以线程 ID 标记生效者，旧线程退出前收到的事件放行，避免重挂时重复处理。
  - 新增 `taskbar::toggle_from_strip(app, source)`，钩子（`hook`）与前端 onClick（`webview`，钩子安装失败时的后备）共用；日志记录来源、结果，以及按下时嵌入条是否在任务栏最上层（取证用）。
  - 删除第 3 轮的置顶守护 `start_zorder_keeper` 及其测试：点击已不依赖层级，继续与资源管理器抢层级只会带来闪烁与无谓开销。
  - `Cargo.toml` 显式声明 windows 的 `Win32_System_LibraryLoader` 特性（已被其它依赖启用，Cargo.lock 不变）。
  - 已知限制：只处理物理左键；系统设置了左右键互换的用户不在本轮覆盖范围。
- 测试：`taskbar_click` 4 条（按下吞掉/松开切换、按下后在外松开只吞不切、外部开始的点击放行、只有完全露出的嵌入条可点）先 RED 后 GREEN。
- 复验：Rust 194 passed / 1 ignored，fmt / clippy（`-D warnings`）/ check 通过；`pnpm typecheck` 通过、前端 53 files / 507 tests 通过；Cargo.lock 无变化。待用户第 5 轮真机验证。
